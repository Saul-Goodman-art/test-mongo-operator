# Orders service (Go) + Logger + Kafka + MongoDB — Helm + kind

Я переработал Helm chart так, чтобы **MongoDB, ZooKeeper и Kafka** разворачивались
не как Bitnami-зависимости, а как собственные Deployment/Service с 
образами, которые Kubernetes будет тянуть прямо с Docker Hub.
Ниже подробно описано, **что изменилось** и **какие новые файлы** появились (с примерами содержимого).

---

## Кратко — что изменилось

1. **Убраны зависимости Bitnami** из `Chart.yaml`. Теперь chart не использует `helm dependency` для mongo/kafka.
2. **Добавлены Kubernetes-манифесты** (Deployment + Service) для:
   - MongoDB (`mongo-deployment.yaml`, `mongo-service.yaml`)
   - ZooKeeper (`zookeeper-deployment.yaml`, `zookeeper-service.yaml`)
   - Kafka (`kafka-deployment.yaml`, `kafka-service.yaml`)
3. **Модифицирован Job миграции**: он теперь использует официальный образ `mongo` (из Docker Hub) для вставки трёх заказов.
4. **values.yaml** расширен: добавлены секции `mongo`, `zookeeper`, `kafka` с настройками образов и базовых параметров.
5. **README** обновлён: теперь нет `helm dependency update`; вместо этого — инструкции по прямому pull-у образов (и опция загрузки образов в kind, если хочешь избежать скачивания).

- Ты просил не тянуть Mongo/Kafka через Bitnami-Helm — я заменил чарты на простые Deployment'ы с образами с Docker Hub. Это делает chart самодостаточным и прозрачным: ты контролируешь точные образы и теги в `values.yaml`.
- Для Kafka я оставил классическую связку ZooKeeper + Kafka (одноузловая) — простая и рабочая для локального dev/kind. При желании можно заменить на Redpanda (без ZK) — скажи, сделаю.

## Новые файлы в `helm-chart/templates/`
Я добавил шесть новых файлов. Ниже — их подробное описание и полный пример содержимого.

### 1) `mongo-deployment.yaml`
**Что делает:** разворачивает одноподный MongoDB `mongo:5.0`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "orders-app.fullname" . }}-mongodb
  labels:
    app: orders-mongodb
spec:
  replicas: 1
  selector:
    matchLabels:
      app: orders-mongodb
  template:
    metadata:
      labels:
        app: orders-mongodb
    spec:
      containers:
        - name: mongo
          image: "{{ .Values.mongo.image.repository }}:{{ .Values.mongo.image.tag }}"
          imagePullPolicy: {{ .Values.mongo.image.pullPolicy }}
          ports:
            - containerPort: 27017
          volumeMounts:
            - name: datadir
              mountPath: /data/db
      volumes:
        - name: datadir
          emptyDir: {}
```

### 2) `mongo-service.yaml`
**Что делает:** ClusterIP-сервис для MongoDB (внутри кластера).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ include "orders-app.fullname" . }}-mongodb
  labels:
    app: orders-mongodb
spec:
  type: ClusterIP
  ports:
    - port: 27017
      targetPort: 27017
      protocol: TCP
      name: mongo
  selector:
    app: orders-mongodb
```

### 5) `kafka-deployment.yaml`
**Что делает:** разворачивает один брокер Kafka, использующий ZooKeeper. Важно: я настраиваю `KAFKA_ADVERTISED_LISTENERS` так, чтобы другие поды могли подключаться по `kafka:9092`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "orders-app.fullname" . }}-kafka
  labels:
    app: orders-kafka
spec:
  replicas: {{ .Values.kafka.replicaCount }}
  selector:
    matchLabels:
      app: orders-kafka
  template:
    metadata:
      labels:
        app: orders-kafka
    spec:
      containers:
        - name: kafka
          image: "{{ .Values.kafka.image.repository }}:{{ .Values.kafka.image.tag }}"
          imagePullPolicy: {{ .Values.kafka.image.pullPolicy }}
          env:
            - name: KAFKA_BROKER_ID
              value: "1"
            - name: KAFKA_ZOOKEEPER_CONNECT
              value: "{{ include "orders-app.fullname" . }}-zookeeper:2181"
            - name: KAFKA_LISTENERS
              value: "PLAINTEXT://0.0.0.0:9092"
            - name: KAFKA_ADVERTISED_LISTENERS
              value: "PLAINTEXT://{{ include "orders-app.fullname" . }}-kafka:9092"
            - name: KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR
              value: "{{ .Values.kafka.config.offsetsTopicReplicationFactor }}"
            - name: KAFKA_TRANSACTION_STATE_LOG_MIN_ISR
              value: "1"
            - name: KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS
              value: "0"
          ports:
            - containerPort: 9092
```

> Примечание: `KAFKA_ADVERTISED_LISTENERS` указывает на сервис `{{ .Release.Name }}-kafka`. Клиенты внутри кластера могут использовать `kafka:9092` (в нашем chart — это `{{ .Release.Name }}-kafka:9092`).

## Обновлённый `mongo-migration-job.yaml`
**Что изменилось:** использую официальный `mongo` образ для выполнения JS-скрипта вставки трёх документов. В job есть initContainer «wait-for-mongo», чтобы дождаться доступности Mongo.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "orders-app.fullname" . }}-mongo-migration
spec:
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      initContainers:
        - name: wait-for-mongo
          image: busybox
          command: ['sh','-c','until nslookup {{ include "orders-app.fullname" . }}-mongodb; do echo waiting; sleep 2; done']
      containers:
        - name: migrate
          image: "{{ .Values.migration.image.repository }}:{{ .Values.migration.image.tag }}"
          command: ["bash","-lc"]
          args:
            - |
              echo "Waiting for Mongo to accept connections..."
              until mongo --host {{ include "orders-app.fullname" . }}-mongodb --eval 'db.adminCommand({ ping: 1 })' > /dev/null 2>&1; do sleep 1; done
              mongo --host {{ include "orders-app.fullname" . }}-mongodb ordersdb --eval '
                db.orders.insertMany([
                  {customer: "Ivan", item: "Book", amount: 12.5},
                  {customer: "Anna", item: "Pen", amount: 2.3},
                  {customer: "Sergey", item: "Notebook", amount: 5.0}
                ])
              '
```

> Обрати внимание: для `mongo:5.0` команда `mongo` доступна. Если хочешь использовать `mongo:6.x`, нужно заменить вызов на `mongosh` и/или скорректировать команду.

## Ограничения и советы

- **Одноузловая конфигурация** — всё настроено для локальной отладки. Для production нужно включить persistence, репликацию и безопасную аутентификацию.
- **Kafka**: в такой конфигурации используется ZooKeeper. Если предпочитаешь без-ZK (KRaft / Redpanda) — могу переписать манифесты под Redpanda (проще) или под Kafka KRaft (сложнее в конфиге).
- **MongoDB shell**: я указал `mongo:5.0` чтобы миграция работала через `mongo`. Если хочешь современные образы (6.x), скажи — я перепишу миграционный job под `mongosh`.
- **Сеть в kind**: все сервисы ClusterIP — API и logger доступны внутри кластера. Для тестов используй `kubectl port-forward` на сервис API.
